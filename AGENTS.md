# Tephramesh agent guide

Keep this file current. Every feature, behavior change, important fix, renamed concept, new invariant, or workflow change must update `AGENTS.md` in the same work. Describe shipped behavior as current and unfinished behavior as pending; never blur the two.

## Product

Tephramesh is an Obsidian plugin that manages a dedicated Syncthing mesh for exactly one complete Obsidian vault.

- A **device** is a trusted desktop, laptop, or phone that runs Obsidian and stores the vault in plaintext.
- A **shard** is a generally always-online server. Its managed folder must be Syncthing `receiveencrypted`; devices provide the shard encryption key when sharing, while Tephramesh leaves shard-related Syncthing peer-trust settings unchanged.
- Devices use `sendreceive`. Device-to-device data is plaintext at rest and encrypted in transit by Syncthing. Peer trust is managed only for device-to-device relationships; Tephramesh leaves Syncthing's existing trust choice untouched for every relationship involving a shard, including first setup.
- All devices use one **shard encryption key**. Do not call it a shared password or shard password in user-facing text.
- The intended topology is a complete mesh with `n(n-1)/2` peer relationships.
- The entire vault is always in scope. Do not add selective-sync or exclusion UI. Pending: inspect every managed folder's Syncthing ignore rules and treat active rules as a warning or invalid plan, with a safe way to clear them. Syncthing's own internal files are exempt.

## Security and secrets

- First-instance onboarding may contact only loopback (`localhost`, `127.0.0.1`, or `::1`); its port is configurable.
- Remote Syncthing API endpoints require HTTPS. Store endpoints as protocol, hostname, port, and optional normalized URL path. Legacy endpoints without `path` mean the origin root.
- Encryption setup precedes Syncthing onboarding. When no encrypted plugin configuration exists, the only setup path locally generates a dedicated post-quantum hybrid age identity (`AGE-SECRET-KEY-PQ-1…`) using ML-KEM-768 plus X25519 and shows a one-time backup dialog before continuing. Do not show an existing-identity/public-recipient import form during fresh setup: there is no configuration whose recipient it could recover. When an encrypted configuration already exists, its plaintext public recipient is authoritative and the unlock screen asks only for the matching private identity. Do not accept SSH identities or passphrase encryption.
- Label the fresh encryption/onboarding screen **Tephramesh initial setup** and introduce it with: “Generate a dedicated post-quantum age identity to protect the plugin configuration.”
- The plaintext `data.json` envelope contains only `schemaVersion` (currently `3`), the public `ageRecipient`, and Base64 `encryptedData`. The decrypted versioned payload has the only other schema version (currently `1`) and contains all operational settings and secrets: onboarding state, folder metadata, polling settings, complete instance records, API keys keyed by instance ID, and the shard encryption key. Do not duplicate schema versions inside its `settings` or `secrets` objects. Legacy encrypted snapshots with redundant nested schema fields remain readable and are normalized after unlock. Never add another plaintext configuration field without explicit user approval.
- The age-encrypted configuration stores a hash-linked history of complete protected configuration snapshots. Once configuration signing is initialized, that history is wrapped in a signed configuration envelope containing its monotonic revision, enrollment root, public device-signing keys, signed enrollment certificates, signer key ID, and signature. The Config tab's **Saved config versions** setting is a numeric value from 1 through 10 and defaults to 10; only the newest configured number is retained. A value of 1 retains only the current configuration. History links and snapshot hashes are verified before applying a retrieved configuration, while legacy single-snapshot and unsigned history payloads remain readable for migration. Snapshots are cloned before becoming running state so later runtime edits cannot invalidate their hashes. Config histories already affected by the former in-memory aliasing bug are repaired only when every stored link and metadata hash remains valid; repaired hashes are verified and encrypted again before unlock completes.
- Store the private age identity in local Obsidian Keychain under the fixed ID `tephramesh-age-identity`. Store each installation's private P-256 configuration-signing key, local signing binding, pinned enrollment root, pending manual enrollment state, and last accepted signed revision/hash in Keychain under `tephramesh-device-signing`. Never sync or write either private key to `data.json`; only public signing keys and signed certificates belong inside the age-encrypted configuration. Clear decrypted operational secrets from memory on unload.
- Configuration signing is initialized automatically on the first installation when fresh encryption setup successfully adds the first device; that device becomes the locally pinned self-signed enrollment root and first approver. An existing unsigned configuration can still be initialized explicitly on exactly one installation, which signs the existing encrypted history without changing its operational contents. Other installations generate a manual copy/paste enrollment request containing a new local public key and device binding. An already enrolled installation verifies that binding against either an active device or Known device, displays the resolved device role/name and signing-key fingerprint for explicit review, signs only after a second approval action, and returns a copy/paste approval. The approval screen keeps Review request disabled until a non-empty enrollment request is entered, and re-disables it when the request is edited or cleared. The requesting installation verifies and pins that approval before it may save configuration. No enrollment step polls localhost, adds plaintext envelope fields, or synchronizes unsigned enrollment requests. Losing every enrolled private signing key requires explicit Delete Config/reset and a new signing bootstrap.
- Configuration-signing authorization is independent of active mesh participation. Active devices and Known devices may represent Obsidian installations and may enroll signing keys; this includes phones that run Obsidian and Tephramesh but expose no queryable Syncthing API. After approval, those installations can verify and sign protected configuration changes without any API request to their own Syncthing device. Shards cannot enroll signing keys. The full Syncthing device ID is the stable binding label, while endpoint URLs remain mutable transport locations.
- Signing initialization and enrollment candidate lists exclude active or Known devices whose binding or full device ID is already authenticated in the signed enrollment list, while authenticated-installation status resolves names from the complete active and Known device list.
- A newly synced installation must show the unlock/import screen until the matching identity is entered once. Validate that the identity derives the configured recipient before storing it. Reload and decrypt externally synced settings through `onExternalSettingsChange`.
- Migrate legacy per-secret Keychain data into the encrypted bundle during encryption setup, remove legacy secret-name fields from saved configuration, and fail safely if a required legacy API key is unavailable. Old Keychain values cannot be programmatically deleted.
- API keys authenticate REST calls, not the normal Syncthing web UI. Never place an API key in a URL.
- Generated shard keys are `sk-` followed by 32 cryptographically random alphanumeric characters.
- Successful age setup automatically generates the shard encryption key before the first encrypted save. Legacy migration preserves an existing shard key and only generates one when none previously existed.
- Store the generated shard key inside the age-encrypted bundle. Legacy `shardEncryptionKeyHash` fields are ignored during migration; the protected shard key is authoritative. Once it exists, show it masked and disabled and expose no replacement control.

## Current behavior

- Signing is the final settings tab, after Config.

- In the approval-required Signing view, the **This installation** request control appears before the already enrolled installations list. After this installation generates a request, the request's stored device binding and signing key appear as a yellow Pending approval device independent of the dropdown's current selection or settings rerenders. Completing enrollment removes that pending state and immediately renders the installation normally from the authenticated signed enrollment chain. On the approving installation, reviewing a valid request changes the second-step **Approve [device]** button to yellow. Approving it adds the requesting device as a yellow Pending approval entry while the settings screen remains open. Its signed approval is copied automatically and remains available through a **Copy approval** button directly on that pending device; there is no separate approval code field or card. Once synchronized signed configuration contains that signing key, the pending entry and generated approval disappear and the device displays as a normal authenticated installation.

- Settings use tabs: **Topology** first and selected by default, then **Instances**, **Vault**, **Signing**, and **Config**. The Signing tab shows the same yellow status dot as Topology whenever this installation is not enrolled for configuration signing, including unsigned and approval-required states. In the approval-required state, its status message refers to the local installation as a “tephramesh device.” The Topology, Instances, Vault, and Config tabs do not render their former introductory heading text; Config also omits its former warning paragraph. Signing omits its former Configuration signing heading. The Instances tab presents active Devices, Shards, and Known peers in separate sections, separates populated sections with a divider, keeps the Shards section visible when empty, and places each section's Add action on the right side of its heading. It identifies role by section heading rather than a card badge. The Signing tab contains configuration-signing status and the applicable initialize, manual request/approval, or enrolled-installation approval controls. A generated enrollment approval is copied automatically and remains visibly available with a dedicated copy action until the settings screen closes. Enrolled state shows a color-coded list of every authenticated installation without a separate section heading, with its Active, Known, or no-longer-configured status, device ID segment, public-key fingerprint, approver, authentication time, local-installation marker, and enrollment-root marker. The approval-required view separately displays the already enrolled installations, including their current source, device ID segment, key fingerprint, and enrollment-root marker, so the user knows where to send the request. An installation that can decrypt signed configuration but is not enrolled is locked to the Signing tab; only the Signing tab is shown until approval, mesh API polling and reconciliation are suspended, and the protected data may be read provisionally only to complete enrollment. Configuration-changing controls remain unavailable until approval. Config provides one compact config-version selector containing every retained version, its version number, save time, and current marker. It initially hides the decrypted view and offers **Display** for the current selection; displaying it reveals the read-only, visibly styled decrypted code-block view and changes the action to **Restore** for older selections. Changing the selection displays that snapshot and returns the action to **Restore**. Restoring applies its settings and secrets as a new latest signed version, preserves the current history-retention policy and existing chain, and does not directly change Syncthing or vault files. Decrypted config is hidden again when Config is left or the settings window closes. The view includes the single inner schema version and secrets. Private age and device-signing keys remain excluded because they are stored only in the local Obsidian Keychain. There is no Shards tab or shard-key display: the key is generated automatically during age setup, remains hidden in the normal settings UI, and shard management stays in Instances.
- Initial setup asks for the API key, not a device name. Tephramesh discovers the local name by matching `/rest/system/status` `myID` to `/rest/config/devices`.
- Device and shard setup puts a complete Syncthing URL first. Parsing it must populate and visibly synchronize protocol, hostname, effective port (80/443 when omitted), and normalized reverse-proxy path. Component edits update the full URL. Reject credentials, query strings, fragments, unsupported schemes, invalid URLs, and URL syntax injected through hostname or path components. Every REST request revalidates the stored endpoint before attaching its API key. `endpointUrl()` must include the path so both REST requests and clickable instance links work behind a subpath proxy.
- Device names remain Syncthing-authoritative. Refresh them from reachable instances approximately every five minutes and persist external changes. Poll identity, version/platform, device names, and managed-folder configuration on that same metadata cadence; frequent status polling requests only live folder status and connection counters, plus state-dependent scan progress or needed paths. Each instance runs its own bounded request sequence concurrently with every other instance, so a slow host neither delays nor increases queries to healthy hosts.
- Setup has separate **Test** and **Add** actions. Add stays disabled until the current form state has passed Test; any edit invalidates the test result.
- The add-device dialog's **Cancel** action uses the red error color to distinguish dismissal from the setup actions.
- For additional instances, the folder-path field starts disabled. A successful Test preserves an existing managed-folder path or suggests `<default Syncthing folder path>/<Tephramesh folder ID>`, then enables the field for review. Endpoint or API-key changes clear and relock the suggestion.
- Add creates a missing managed Syncthing folder from `/rest/config/defaults/folder`, posts it through the REST API, and verifies creation. Users should not need the Syncthing web UI for folder creation.
- Before adding another instance, perform a fresh status check against every existing instance. Block without mutation and show a warning unless all are reachable, `idle`, have no pending files/bytes, and report no folder errors.
- If Test successfully discovers a new instance but Add is blocked only because the active mesh fails that readiness gate, persist the instance and API key in the encrypted configuration with `setupState: "pending"`; do not create/share its folder yet. Show a yellow Pending setup action on its Instances card so the user does not need to re-enter the form. Pending instances are excluded from the active-mesh safety gate, folder-label propagation, and reconciliation as existing peers. A retry must recheck active-mesh readiness, revalidate the pending endpoint's full device ID, refresh its Syncthing-authoritative name, verify or create its managed folder with the expected path/type, reconcile it bidirectionally with every active instance, and clear `setupState` only after success. Keep it pending after any partial failure so retry and removal remain safe.
- After the safety gate, configure the new and every existing instance bidirectionally as Syncthing device and managed-folder peers. This includes direct sharing between every pair of shards when a second or later shard is added. The newly created folder must be shared immediately rather than left `Unshared`; apply the encryption key only to device-to-shard folder shares. Tephramesh does not set, verify, or report peer trust for any relationship involving a shard, since a shard can also host ordinary folders. Shard-to-shard peers receive no encryption key because they exchange ciphertext already stored by their `receiveencrypted` folders. Use the shared `meshPeerPolicy()` for both plans and live reconciliation, and verify every managed field by reading it back.
- Removing an instance requires explicit confirmation. Either active device can be removed once another active device exists, but the last active device can never be removed; removing the primary promotes another active device. Pending devices do not satisfy the remaining-device requirement. Verify all affected APIs first, remove that device from the remaining managed-folder shares, delete the managed folder configuration on the selected Syncthing instance, verify each change, and only then forget it in plugin settings. Syncthing folder removal does not delete the files on disk; say so clearly in the warning and success notice.
- New folder IDs are `tephramesh-` plus eight lowercase alphanumeric characters. Never change an existing configured folder ID.
- Folder labels are desired state. Debounce edits, update every reachable instance, verify by reading back, warn about partial success, and retry during status refresh.
- Syncthing instance status polling runs only while the Tephramesh settings screen is open. Its default refresh interval is one second; options are 1, 5, 10, 30, and 60 seconds. Instance cards have no manual status-refresh button because polling keeps them current automatically. Directly beneath it, the Vault tab has a separate note sync icon refresh interval. That background poll remains active outside settings because it drives File Explorer decorations; it defaults to five seconds and offers 1, 5, 10, 30, and 60 seconds.
- The Vault tab exposes an **Offline timeout** setting, defaulting to five seconds with options of 1, 5, 10, 30, and 60 seconds. A device or shard is considered offline/unavailable when no successful status check has completed within that window; this freshness rule applies to instance cards, Topology operating counts, and aggregate status.
- Status checks for all instances start concurrently, and each instance check is bounded by the configured offline timeout. A slow or hung device or shard is marked unavailable without delaying status updates for other instances or preventing the next polling cycle.
- Each instance performs its individual Syncthing REST requests sequentially to avoid exhausting Obsidian/Electron network resources with a burst of requests, while different instances remain concurrent.
- Timed-out status checks are retained as in-flight because Obsidian's `requestUrl` calls cannot be aborted; subsequent polling reuses the existing check per instance instead of creating orphaned request batches that can exhaust Chromium/Electron network resources.
- Changing either the status refresh interval or offline timeout immediately requests a fresh status check for every configured device and shard. If a cycle is already running, one forced refresh is queued to start when it finishes.
- Changing the Offline timeout saves the new value and immediately forces a fresh Syncthing API status check for every configured instance before the UI re-evaluates availability.
- The Config tab ends with a warning-styled **Delete Config** action with explicit confirmation only on an installation enrolled for configuration signing. Unsigned and approval-required installations do not expose or permit config deletion. Deletion removes the vault's Tephramesh `data.json`, resets the local device-signing key and enrollment binding, and returns the plugin to initial setup without changing Syncthing configuration, vault files, or the private age identity stored in the local Obsidian Keychain.
- Each instance card exposes that host's Syncthing managed-folder **Pull order** (`order`) setting (random, alphabetical, smallest first, largest first, oldest first, or newest first). Changing it persists and verifies only that host's value, restoring the previous value if the update fails.
- The Vault tab exposes Tephramesh-managed ignore rules as one pattern per line, blank by default. Tephramesh stores only its managed rules in the encrypted configuration and writes them inside a delimited `TEPHRAMESH MANAGED RULES` section in each instance's defaults and existing managed folder through `/rest/config/defaults/ignores` and `/rest/db/ignores`; editing replaces only that section and preserves user rules outside it. The legacy `globalIgnoreRules` configuration field is discarded when loading older snapshots and is no longer read or written; `managedIgnoreRules` is authoritative.
- The Vault tab exposes a numeric host threshold for note sync icons. Its default is the configured shard count plus one; the icon clears when a note is available on at least that many active devices or shards. Choices are limited to the current active mesh size and are clamped when the mesh changes.
- Folder status uses green for idle and Syncthing-like light blue for scanning or syncing. Treat Syncthing's `sync-preparing` and `sync-waiting` states as syncing for both instance-card color and aggregate Topology status, while retaining the precise state text on the card. Instance cards show the managed folder's Syncthing `stateChanged` time as its latest updated time in the user's local date/time format. Scanning shows event-backed percentage from `FolderScanProgress`; stale events older than `stateChanged` are ignored. Syncing shows a live integer completion percentage derived from global and needed bytes, falling back to global and needed file counts when byte totals are unavailable; floor incomplete values so they never display as 100% prematurely. The syncing line also shows instance-wide download and upload rates calculated between consecutive `/rest/system/connections` cumulative-byte samples. Sample traffic during every status refresh, including idle periods; show `measuring…` until a valid prior sample exists and after counters reset. These rates intentionally include traffic from every Syncthing folder on the instance.
- The Obsidian File Explorer prefixes Markdown notes that any active mesh instance still needs, along with every ancestor folder containing those notes, with a prominent blue Obsidian `refresh-cw` icon. These are DOM decorations only and never change filenames, folder names, or note contents. Tephramesh polls Syncthing local- and remote-need data at the configured note sync icon interval, preferring the primary device and falling back to other reachable devices; it retains the last known indicators if no active device can answer. Shards are checked as remote peers but are not query sources because their local filenames are encrypted.
- Syncthing local- and remote-needed file pagination is bounded to 100 pages and 100,000 paths per query. Tephramesh validates every returned page and rejects oversized, malformed, or consecutively repeated full pages instead of accumulating indefinitely or treating partial data as complete.
- Instance cards show a compact `Device` or `Shard` role badge followed by the Syncthing-authoritative name, the first seven-character device-ID segment, and the live Syncthing version together in the heading. Show only the returned version string (for example, `v2.1.2`), without a `Syncthing` prefix. Device badges use Obsidian's active purple accent; shard badges use orange so they remain distinct from blue scanning/syncing states. Both use high-contrast accent text. Do not render the role as a plain `Device: ` or `Shard: ` text prefix. The version updates with normal status refreshes and uses a neutral placeholder until known. Retain the full device ID internally.
- Instance cards show a platform logo immediately after the instance name for macOS, Windows, and Linux. Derive it from the `os` field returned by Syncthing's `/rest/system/version` response during normal status polling, keep it only in runtime memory, and omit the logo for unavailable or unsupported operating systems.
- Active device cards list the local Syncthing paths they still need whenever their managed folder reports pending files. The list refreshes with normal instance status polling and is scrollable when long. Shard cards do not show pending paths because their local filenames are encrypted.
- Instance cards override generic Setting-row minimum height, use a 24px-equivalent top inset, and add no explicit bottom padding. This shifts the three-line content block down to visually center it in the theme's card area while minimizing empty space beneath the status line. Keep this scoped to `.tephramesh-instance-card` so Vault and other settings retain normal spacing.
- Instance URLs appear alone on the next line, are clickable, use Obsidian's link/accent color, and never embed credentials.
- Every instance has an Edit URL action. The edit dialog may change only protocol, hostname, port, and reverse-proxy path; it reuses the protected API key and never changes the instance ID, kind, folder path, or full Syncthing device ID. Save remains disabled until Test succeeds for the exact current endpoint and `/rest/system/status` reports the instance's existing full device ID. Any URL/component edit invalidates the test. Apply and persist the endpoint only after that identity check.
- Instances on the Instances tab can be reordered by dragging the grip handle beside an instance name onto a new card position. The numeric `displayOrder` value is stored on each instance in the encrypted configuration; legacy instances are assigned their existing array order and new instances are appended.
- Every active device and shard card has a pause/resume action for its local managed folder. The action patches Syncthing's native folder `paused` setting, verifies the updated folder configuration, and shows paused state in yellow. Pausing is local to the selected instance; paused folders block add/pending-setup readiness and mesh repair until resumed. Pending instance cards do not expose the action until setup completes.
- Notices use a colored first line: green success, yellow warning, red error.
- The Topology tab has separate **Operating now** and **Configured** sections, in that order. Its tab label begins with a status dot that mirrors the validation health dot and updates between healthy, warning, and incomplete-plan states. Operating now places the live runtime-state bubble immediately to the right of the heading, removes explanatory reachability text, keeps the live health warning/status aligned at the far right, and omits the standalone `unavailable` runtime badge. It counts only active instances with a successful current status check, so offline/unavailable hosts are omitted and its complete-mesh connection count is recalculated from reachable instances. Configured contains only the active configured device, shard, and complete-mesh connection counts; pending configuration entries do not contribute until setup completes. The validation header says **Healthy** in green when all active participants are reachable, and **Warning** in yellow when one or more are offline, with no supporting subtitle. It also shows live mesh status badges, storage behavior, and responsive layout; the separate peer-encryption subtitle is omitted. Aggregate status is unavailable when an active instance fails, otherwise prioritizes scanning over syncing, and reports idle only when every active configured folder is idle. When one or more instances have pending setup, show a separate `pending` badge alongside the active status instead of collapsing everything to `checking`. Use normal state colors: green idle, blue scanning/syncing, red unavailable, yellow pending.
- The Topology tab's Operating now summary shows the global file count and global folder size in separate cards; the size is formatted in binary MB or GB units when Syncthing reports global bytes. Topology metric cards reflow fluidly as the settings window resizes, use a compact two-column layout on mobile, and keep metric values on one line while labels wrap within their cards at narrow widths.
- Operating now metric values remain at the larger metric size while their labels use a smaller relative size; Configured metric typography is unchanged.
- The Topology tab's Operating now Device and Shards cards are green when every configured host of that role is online and yellow when one or more hosts of that role are unavailable. Connections and global file/size cards retain the neutral metric styling.
- The Topology tab audits reconciliation state at startup, approximately every five minutes, and on demand. It reports healthy, checking, repairing, unavailable, or an itemized list of configuration issues. While a new audit is checking, the previous completed issues and repair-blocking explanation remain visible until the audit result replaces them. The audit reads identity, devices, folders, pending invitations, and runtime folder state from every active instance. Repair is enabled only when every instance is reachable, identities/paths/types are unambiguous, and every existing managed folder is idle and complete. The preview distinguishes repairable drift from blocking unsafe configuration.
- Reconciliation refreshes immediately when runtime availability changes so its per-device and per-shard results do not remain stale after a host recovers or becomes unavailable. Its REST reads run sequentially per host, while hosts remain concurrent, to avoid Chromium/Electron request bursts.
- Reconciliation does not wait on hosts already known to be unavailable. It reports those instances immediately, and bounds each reachable host's audit by the configured offline timeout. Timed-out audit requests are retained and reused rather than duplicated because Obsidian's `requestUrl` cannot abort them.
- Mesh repair is idempotent and verified. It creates missing managed folders with shards first, updates folder labels, ensures every peer device and folder share with the correct trust and encryption policy, removes unregistered peers only from the managed Tephramesh folder, and then re-audits the complete mesh. It preserves unrelated Syncthing devices, folders, and unknown configuration fields. Partial failures remain visible and can be retried; Tephramesh never attempts rollback-by-deletion.
- Known peers are persisted outside the active mesh. When reconciliation finds a managed-folder share to a device outside Tephramesh, it shows the Syncthing name and short device-ID segment with an Add as Known action. Known peers use a yellow role badge, are excluded from topology counts and mesh planning, and are preserved by reconciliation repair. A Known peer can be removed after confirmation; removal forgets only the Known record without immediately changing Syncthing or files, and future repair no longer preserves its managed-folder share.

## Implementation map

- `src/settings-tab.ts`: tabbed settings, instance/status UI including persisted drag-and-drop display ordering, shard-key UI, and topology summary.
- `src/instance-modal.ts`: setup, Test/Add gating, device discovery, and folder creation flow.
- `src/edit-endpoint-modal.ts`: endpoint-only editing with Test/Save gating and full device-ID identity verification.
- `src/remove-instance-modal.ts`: destructive-removal confirmation and failure handling.
- `src/delete-config-modal.ts`: destructive plugin-configuration deletion confirmation.
- `src/syncthing-client.ts`: Syncthing REST client.
- `src/syncthing-pagination.ts`: bounded, validated local- and remote-needed file pagination.
- `src/config-signing.ts`: canonical P-256 signing, enrollment requests and approvals, certificate-chain verification, signed configuration envelopes, and rollback anchors.
- `src/security.ts`: endpoint validation, identifiers, key generation/validation, shortening, and SHA-256 hashing.
- `src/secret-bundle.ts`: native age key-pair validation, versioned secret-bundle encryption/decryption, and the fixed local identity name.
- `src/age-identity-backup-modal.ts`: one-time private-identity backup and clipboard UI after generation.
- `src/topology.ts`: deterministic full-mesh planning and trust/encryption placement.
- `src/reconciliation.ts`: pure reconciliation drift inspection and repair-readiness checks.
- `src/syncthing-device.ts`, `src/syncthing-folder.ts`, `src/syncthing-scan.ts`: pure helpers with focused tests.
- `src/note-sync.ts`: derives File Explorer folder indicators from pending note paths.
- `src/notices.ts`: severity-colored notices.
- `styles.css`: settings, topology, status, links, and notice presentation.
- `docs/architecture.md`: trust matrix and planned reconciliation sequence.

## Development and release workflow

- License: GPL-3.0-only.
- Required validation for code changes: run `npm test` and `npm run build`. The current baseline is 85 tests across fifteen test files; update this count here only when it materially helps orientation.
- When a user prompt ends with `; build` or `;build`, run `./test.sh build` after completing the requested work so the plugin is automatically built and deployed to the testing vault. If the build is blocked, report the exact blocker instead of treating the task as complete.
- When a user prompt ends with `; git` or `;git`, save the requested work in the local repository by creating an appropriate commit, then push that commit to the repository's configured remote (usually GitHub). Inspect the repository status and remotes first, identify the exact files and hunks changed by the current task, and stage only those explicit paths/hunks; never use broad staging such as `git add -A`, `git add .`, or `git commit -a`. Treat pre-existing, concurrent, and unrelated worktree changes as out of scope and leave them unstaged. If a file contains both current-task and other-task changes, stage only the current-task hunks when they can be separated safely; otherwise stop and report the overlap rather than committing the file. Before committing, verify the staged diff contains only the current task's changes, and after committing verify the push succeeds. If committing or pushing is blocked, report the exact blocker instead of treating the work as complete.
- `main.js` is a generated production bundle and is intentionally ignored by Git. It is still required by Obsidian, BRAT, and community-plugin releases: local build/deploy creates it, and the tag-based release workflow rebuilds and attaches it alongside `manifest.json` and `styles.css`.
- Ignore machine-local/generated files: `node_modules/`, `main.js`, source maps, TypeScript build metadata, coverage, logs, `.env` variants except `.env.example`, `.idea/`, `.vscode/`, `.DS_Store`, and any root `data.json`. Never commit plugin runtime configuration even though its protected payload is age-encrypted. Commit the lockfile, manifest, versions map, stylesheet, source, tests, documentation, and release workflow.
- `./test.sh build` installs locked dependencies, builds, and copies `main.js`, `manifest.json`, and `styles.css` to both the `Notebox` testing vault and `/Users/willjasen/Library/Mobile Documents/iCloud~md~obsidian/Documents/testing`. - `./test.sh clear` removes only the testing vault's Tephramesh `data.json`, then automatically performs the build/deploy flow. It cannot remove the local `tephramesh-age-identity` Keychain entry.
